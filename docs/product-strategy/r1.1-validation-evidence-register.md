## 1. Purpose & Integrity Rules

This register is the **single auditable source of truth** for all primary customer evidence collected during R1.1. Every claim made in the R1.1 Synthesis Report and every check in [r1.1-r2-entry-criteria.md](file:///c:/Users/Iyyappan%20E/Folders/SDE/Round%203-HR%20Interview/PROJECTS/Projects/EPAMS/docs/product-strategy/r1.1-r2-entry-criteria.md) MUST trace back to one or more verified `Evidence ID` rows in this file.

### Mandatory Integrity Guardrails
1. **Zero Fabrication:** Never invent respondents, interview transcripts, quotes, spend figures, survey counts, or concept reactions. This register intentionally starts with **`0` rows** until live R1.1 interviews and surveys occur.
2. **Strict PII Exclusion:** Never record participant full names, email addresses, phone numbers, company names, or identifiable customer secrets in this repository file. Use strictly anonymized codes (`INT-01`, `SURV-001`) mapped only in a separate, access-controlled offline recruitment log.
3. **Preserve Contradicting Evidence:** Every interview that disconfirms `H1`, `H2`, `H3`, or `H4` (e.g., *"We prefer cloud SaaS"*, *"We require built-in CMDB"*, *"GLPI is already good enough"*) MUST be logged with the same rigor as supporting evidence. Cherry-picking disqualifies the R2 gate.
4. **No Speculative Synthesis in Raw Rows:** Log concrete behavioral facts (what happened in the last `30–90` days, exact tools used, exact blockers) separately from subjective opinions.

## 2. Field Schema Specification

| Column | Allowed Format / Values | Rules & Notes |
| :--- | :--- | :--- |
| **`Evidence ID`** | `EV-001`, `EV-002`, ... | Sequential unique identifier; never reused even if a row is later marked `DISQUALIFIED` |
| **`Date`** | `YYYY-MM-DD` | Date the interview, concept test, or survey batch occurred |
| **`Participant code`** | `INT-01` .. `INT-24` (interviews) or `SURV-BATCH-01` / `SURV-001` (surveys) | Strictly anonymized; no PII or company names |
| **`Organisation segment`** | Band + industry type + deployment posture (e.g., `150–300 | Healthcare | Self-Hosted`, `301–750 | FinTech | Hybrid`) | Must map to the recruitment bands in `r1.1-participant-recruitment-plan.md` |
| **`Role`** | `Head of IT`, `SysAdmin`, `HR Ops`, `InfoSec`, `Dept Manager`, `Support Lead`, `VP Ops`, `Employee` | Exact functional role of the participant |
| **`Research method`** | `Discovery Interview`, `Concept Test (P1/P2/P3)`, `Commercial Walkthrough`, `Secondary Survey` | Distinguishes primary behavioral interviews from secondary survey data |
| **`Finding`** | Concise, factual summary of observed behavior, incident, requirement, or reaction | Quote verbatim (anonymized) where helpful; mark unverified opinions explicitly as `[Opinion]` |
| **`Supporting hypothesis`** | `H1`, `H2`, `H3`, `H4`, `None`, or `Mixed` | Hypotheses from `r1.1-hypothesis-validation-scorecard.md` supported by this finding |
| **`Contradicting evidence`** | `None` OR explicit description of how this finding challenges `H1`–`H4`, `R1-DEC-001`–`005`, or scope assumptions | Never leave blank; write `None` only after actively checking for disconfirming signals |
| **`Confidence`** | `High`, `Medium`, `Low` | `High` = concrete recent (`<= 90` days) behavioral incident/artifact or corroborated across `>= 2` roles in same org; `Medium` = clear single-participant behavioral report; `Low` = hypothetical preference or survey-only input |
| **`Source`** | Session note reference (e.g., `Interview Notes INT-01 §A3`, `Survey Export Q9–Q11`) | Allows offline verification by the research lead |
| **`Status`** | `RAW`, `VERIFIED`, `SYNTHESIZED`, `DISQUALIFIED` | `RAW` = logged within 24h; `VERIFIED` = cross-checked against notes/recording; `SYNTHESIZED` = rolled into scorecard; `DISQUALIFIED` = failed screening criteria (retained for auditability) |

## 5. Logging Cadence & Audit Procedure

1. **Within `24` hours of every interview:** Log raw behavioral findings (`Status: RAW`) while memory and notes are fresh.
2. **Weekly synthesis checkpoint:** Review all `RAW` rows against interview notes/recordings, assign `Confidence`, explicitly verify the `Contradicting evidence` column is populated, and promote verified rows to `VERIFIED`.
3. **Pre-R2 Gate Audit:** Reconcile every count in [r1.1-hypothesis-validation-scorecard.md](file:///c:/Users/Iyyappan%20E/Folders/SDE/Round%203-HR%20Interview/PROJECTS/Projects/EPAMS/docs/product-strategy/r1.1-hypothesis-validation-scorecard.md) and [r1.1-r2-entry-criteria.md](file:///c:/Users/Iyyappan%20E/Folders/SDE/Round%203-HR%20Interview/PROJECTS/Projects/EPAMS/docs/product-strategy/r1.1-r2-entry-criteria.md) directly against `VERIFIED` / `SYNTHESIZED` rows in Section 3 before requesting user approval to enter R2.
